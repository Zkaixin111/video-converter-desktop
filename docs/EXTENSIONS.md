## 2. 优先级模型

排序不靠直觉，按五个维度打分（1–5 分，越高越好），加权求和：

| 维度 | 权重 | 打分含义 |
|---|---|---|
| **用户价值** V | 30% | 需求频次 × 每次返工成本。5 = 不做就得手工绕路，4 = 高频不便，3 = 特定场景有用，2 = 少数人用 |
| **复用契合度** F | 20% | 5 = 只加一层薄封装，1 = 要动状态机或重写判定矩阵 |
| **风险与成本** R | 20% | 5 = 纯函数、可单测、不碰回归矩阵；1 = 触碰调度/产物兼容性/打包链路 |
| **前台可见度** S | 15% | 5 = 界面上已经写着「后续版本」或用户会主动找；1 = 用户不知道自己需要 |
| **依赖就绪度** D | 15% | 5 = 前置能力全在；1 = 要先把别的功能做完才能开始 |

`综合分 = 0.30V + 0.20F + 0.20R + 0.15S + 0.15D`

**三条业务判断**（决定了权重为什么这样分，也是后文「优先级依据」反复引用的依据）：

1. **假承诺优先兑现**：界面上已经写「后续版本开放」的位置，权重天然最高——
   用户每次看到那句话都在提醒我们欠了东西（`S` 维度因此单独占 15%）。
2. **能复用的先做**：个人项目最贵的不是代码量，是改完之后回归矩阵变红（`R` + `F` 合计 40%）。
3. **批量场景下的失败成本被低估**：单文件失败只是重转一次，批量失败是「十几个文件全废」。
   所以与稳定性相关的项（磁盘预检、队列持久化）在同等用户价值下排更前。

**关于作品集用途**：这个项目同时是求职作品。若目标是「演示更好看」，
`S`（可见度）可临时上调——深色模式、硬件加速、完成通知这类「一眼能看出差异」的项会前移。
本文默认按「真实工程优先级」排序，选型建议见 §8。

## 4. P0 详述（建议下一轮做完）

### TODO-01 手动画质调节

- **目标**：把「三档预设」升级为「三档预设 + 可展开的高级参数」，让懂的人能填具体数值，
  不懂的人继续用三档。
- **范围**
  - 做：每容器可编辑 `CRF`（或目标码率）、视频编码器、音频码率、编码速度预设（`-preset fast/medium/slow`）；
    高级面板默认折叠，展开即脱离三档；非法值（CRF 超出编码器区间）在渲染层就拦下并给出合法区间。
  - 不做：双遍编码（属 TODO-18）、滤镜链（属 TODO-15）、导入导出参数文件。
- **价值**：预设页现在就写着「画质数值……将在后续版本开放」。对普通用户三档够用，
  但「体积优先转出来还是太大」是**唯一无法通过换档解决**的诉求，只能靠手填数值。
- **优先级依据**：`V=4`（高频痛点但只影响一部分用户）、`F=5`（`planConversion` 已经按 tier
  组装 args，只需把 tier 换成可选的显式参数）、`R=4`（不动状态机，但参数组合需要补单测）、
  `S=5`（界面明写承诺）、`D=5`。**假承诺 + 全复用，是本轮性价比最高的一项。**
- **落点**：`shared/containers.ts`（新增 `QualityOverrides` 类型与合并逻辑）→
  `planner.ts`（`options.overrides` 优先级高于 tier）→ `PresetsPage.tsx`（折叠面板）→
  `shared/types.ts`（`PresetConfig` 增加可选 `custom`）
- **工作量**：M（约 1.5 天，其中一半在写「非法值 → 合法区间」的提示文案与单测）
- **验收要点**：不填任何高级参数时，产物与 `standard` 逐字节一致；CRF 填 0 或 63 被拦下并说明区间；
  直通模式下高级参数不生效且界面明确置灰。

### TODO-02 输出命名模板与冲突策略

- **目标**：让用户在批量场景下控制输出文件名，而不是被动接受「原名 + 序号」。
- **范围**
  - 做：命名模板（支持 `{name}` / `{format}` / `{date}` / `{index}` / `{preset}`）；
    冲突策略三选一：自动加序号（现状）/ 直接覆盖 / 跳过该文件；
    转换页与队列页共用同一套规则，批量时 `{index}` 自动补零对齐。
  - 不做：输出目录结构规则（单独列为 TODO-16）、正则替换、大小写转换。
- **价值**：转 10 个文件后桌面出现 `clip-01(1).mp4`、`clip-01(2).mp4` 是批量功能的直接副作用，
  用户还得手工清理一遍——这等于把省下的时间又还回去。
- **优先级依据**：`V=4`（批量用户的必然摩擦）、`F=5`（`resolveOutputPath` 已经封装了存在性判断，
  模板只是把它参数化）、`R=5`（纯字符串逻辑，可 100% 单测）、`S=3`（用户会想要，但界面上还没入口，
  得自己加）、`D=5`。**唯一一项「风险几乎为零而价值明确」的 P0。**
- **落点**：`core/fs/outputPath.ts`（抽 `OutputNaming` 策略，`ResolveOptions` 增 `template` 与 `onConflict`）
  → `main/store.ts` 默认值 → `SettingsPage` 或 `PresetsPage` 的设置项
- **工作量**：S–M（约 1 天，主要是模板解析的边界：非法占位符、空结果、路径分隔符注入）
- **验收要点**：模板里出现未知占位符时按字面量处理而不是报错；`{index}` 在 12 个文件时补成 `01..12`；
  模板渲染结果为空或含非法字符（`\ / : * ? " < > |`）时回落到原名并提示；覆盖策略下 `.part` 机制仍然生效。

### TODO-03 磁盘空间预检与输出体积预估

- **目标**：开始转换前算出「大概要写多少」，空间不够就提前拦住，而不是转到 80% 报 `E_DISK_FULL`。
- **范围**
  - 做：用源体积 × 判定模式系数（copy ≈ 1.0、remux ≈ 1.05、transcode 按档位 0.45–1.15）估算；
    批量时求和；与目标盘可用空间比较，不足则禁用开始按钮并给出「差多少」；
    `E_DISK_FULL` 的真实报错保留（预检只是提前，不能替代兜底）。
  - 不做：转换过程中动态监控剩余空间（收益低、要加轮询）。
- **价值**：现在是**整批失败**——第 3 个文件写满盘，前面 2 个白转，后面 7 个全红。
  这是本文档里「单位代码量挽回损失」最高的一项。
- **优先级依据**：`V=4`（发生频率不高但一次损失极大）、`F=4`（`core/fs` 已封装，加一个磁盘探针即可）、
  `R=5`（只读检查，失败也不阻断转换）、`S=2`（用户不会主动要求，但遇到一次就会骂）、
  `D=5`。按 §2 第 3 条业务判断（批量失败成本被低估）上调。
- **落点**：新增 `core/fs/disk.ts`（`statfs` 封装 + `estimateOutputBytes(plan, meta)` 纯函数）→
  `ipc/convert.ts` 预检 → `ConvertPage` / `QueuePage` 的阻断提示
- **工作量**：S（约 0.5 天，估算系数要写在注释里并标注「经验值，非精确」）
- **验收要点**：可用空间充足时行为完全不变；不足时开始按钮 disabled 且提示「还需 X GB」；
  估算值在 32 组合回归上与实际体积偏差 < 30%（写进测试，超了就调系数）。

### TODO-04 CI 质量护栏（GitHub Actions）

- **目标**：把「本地记得跑」变成「每次 push 必跑」，防止远程仓库长期处于未验证状态。
- **范围**
  - 做：两个 job——`check`（typecheck + lint + 单测）与 `integration`（`pnpm fixtures` + 集成测试，
    Linux runner 装 ffmpeg 即可，不跑 32 组合全量回归，太慢）；失败时上传日志；
    README 加徽章。
  - 不做：自动打包 Windows 安装包（electron-builder 在 CI 上产 NSIS 需要 wine 或 windows runner，
    成本高于收益）、自动发布 release、代码覆盖率门槛（先把「有没有跑」解决，再谈覆盖率）。
- **价值**：现在**没有任何 CI**（`.github` 不存在）。仓库里有 245 例测试和一条 32 组合回归链，
  但它们只在本地终端里有意义——提交历史里看不出「这次改动坏了没有」。
- **优先级依据**：`V=4`（对维护者是长期复利）、`F=5`（`pnpm test` / `test:int` 命令已齐，只需把
  fixture 生成脚本搬到 CI）、`R=5`（不碰产品代码）、`S=1`（用户看不见）、`D=5`。
  可见度最低但风险为零，属于「顺手就该做的事」。
- **落点**：`.github/workflows/ci.yml`；`scripts/make-fixtures.mjs` 需要确认在 Linux 上无 ffmpeg
  也能跑（或 CI 里先 `apt-get install ffmpeg`）

### TODO-10 并发数调节（1–4）

- **目标**：兑现设置页「可调并发将在后续版本开放」，让多核机器同时跑 2–4 个 ffmpeg。
- **范围**
  - 做：`Settings.concurrency`（1–4，默认 1）；`JobManager` 从单 `activeId` 改为 `activeIds: Set`；

  - 不做：按 CPU 核数自动推荐、单任务内的分段并行。
- **价值**：转 10 个短视频时，串行是「10 次等待」，并发 3 后接近「4 次等待」。这是批量功能的价值放大器。
- **优先级依据**：`V=4`（只对批量用户有意义，但它是批量功能的价值放大器——串行 10 次等待变 4 次）、

- **落点**：`JobManager`（`activeId` → `activeIds`）→ `shared/queue.ts`（状态判定）→

- **工作量**：M–L（约 2–3 天，其中一半是重跑 queue 的 10 条单测 + 7 条集成测试）
- **验收要点**：并发 1 时行为与现在逐条一致（现有测试一条不改）；并发 3 时最多 3 个 ffmpeg 同时存在
  （用进程数断言）；失败策略在并发下仍然只暂停一次而不是三次；删除/重试不会误杀别的任务。

## 7. 明确不做（负向清单）

写在这里是为了以后不再重复讨论：

| 项 | 不做的理由 |
|---|---|
| 云端转码 / 上传 | 产品定位就是「文件不出本机」，这是与在线转换站的核心差异 |
| DRM / 加密内容处理 | 合规红线 |
| 屏幕录制 / 视频剪辑 / 时间轴 | 不在「格式转换」的问题域里，做了会变成另一个产品 |
| 预设文件分享 / 导入社区预设 | 需要服务端与审核，与「无账号、无上传」冲突 |
| 队列内嵌浏览器式多标签 | 队列页已经是单页多任务，加标签只会让状态更难看清 |
